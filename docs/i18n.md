# Internationalisation

Every user-facing string of the command line comes from the message catalogue in [the i18n package](../internal/i18n/i18n.go). The command never formats display text inline. One file per language, one map per file, and the default locale is `en-GB`.

## The catalogue

A message is a key and a value. The keys are constants, so a typo is a compile error rather than a missing string:

```go
const (
	MsgConvertStart   Key = "convert.start"
	MsgConvertSuccess Key = "convert.success"
	MsgConvertLosses  Key = "convert.losses"
)

var enGB = map[Key]string{
	MsgConvertStart:   "Converting %s to %s format.",
	MsgConvertSuccess: "Wrote %s.",
	MsgConvertLosses:  "Features the target format does not carry (%d):",
}
```

A lookup is `T.S(key)` for a whole message and `T.F(key, args...)` for a message with placeholders. The message carries one placeholder per value, so a translator sees the whole sentence and the order of the values. A sentence is never built by joining fragments.

An unknown key returns the key itself. A missing translation therefore stays visible in the output instead of printing an empty line.

## Shipped locales

The project ships two English catalogues:

| Locale | File | Notes |
|---|---|---|
| `en-GB` | [the en-GB catalogue](../internal/i18n/i18n.go) | The default locale and the source of truth. |
| `en-US` | [the en-US catalogue](../internal/i18n/en_us.go) | Carries the entries whose wording differs, and falls back to `en-GB` for the rest. |

A key that the selected catalogue does not carry falls back to `en-GB` at lookup time, so a partly translated locale stays readable.

The project ships no translated locale yet. A new language arrives through machine assistance and a human audit, and the project ships only what a human has reviewed. [The translation guidelines](#translation-guidelines) state the bar.

## Locale selection

The locale comes from the `--locale` flag, and `SWAG_LOCALE` sets the default for the flag. The value is a language tag, for example `en-GB` or `en-US`.

A tag resolves in three steps:

1. An exact match of the tag, ignoring case and treating `_` as `-`. `en_GB` and `en-gb` both select `en-GB`.
2. The language part of the tag, when a catalogue is registered under the bare language. This step matters only when a catalogue uses such a tag.
3. Failure, which lets the command line refuse a typo instead of falling back in silence.

So `en-US`, `en-us`, and `EN_US` select the American catalogue, and `fr-FR` is an error, because no French catalogue is registered. The error names the shipped locales.

A planned change for v0.9.0 detects the active operating system locale and selects it when a catalogue matches. When no catalogue matches, the command falls back to `en-US`, and `en-US` becomes the default locale. [The roadmap](../ROADMAP.md) carries the milestone.

## Add a language

1. Create a file under [the i18n package](../internal/i18n), for example `de.go`, with the locale tag and the map:

```go
const germanLocale Locale = "de-DE"

var deDE = map[Key]string{
	MsgConvertStart: "Konvertiere %s in das Format %s.",
}

func init() {
	Register(germanLocale, deDE)
}
```

2. Translate every key of the default catalogue. [The locale test](../internal/i18n/i18n_test.go) reads both maps and fails when a key is missing or unknown, so an incomplete catalogue fails the build.
3. Add the locale to [the third-party notices](third-party-notices.md) only when the text comes from another work. Translation of our own messages needs no notice.

No change to the command is needed. `Supported()` reports the registered locales, and the flag already accepts the new tag.

## Translation guidelines

These rules govern a translated catalogue, whenever the project accepts one. English documentation and the English catalogue stay the source of truth.

1. A translation must read naturally to a native speaker. Character spacing and punctuation differ between languages, so do not copy the English layout.
2. Machine translation with a human review is allowed. Make the effort to meet rule 1, because a machine does not always infer the context of a phrase.
3. A translator must read and write the target language well enough to review the result by hand. Native fluency is not necessary. A catalogue that no human has reviewed is not accepted.
4. Split a translation into small changes of a sensible size. One change carries one part of the work, so a reviewer reads the scope and the purpose of each change.
5. Work on a branch that names the language and the version, for example `de-translation-0.9.0`. The maintainer merges it into a feature branch first, then cherry-picks to the release branches.
6. Link to a localised reference where one exists, in preference to the English one. A Chinese page of a manual beats its English page for a Chinese reader.
7. The English catalogue and the English documents are the canonical source. When a translation and the English text disagree, the English text wins.
8. No translation is better than a wrong or misleading one. Leave a message out and let the fallback show English.
9. Keep a term in English where the translated form would confuse the reader, or where the reader knows the English name. Format names, flag names, and product names stay unchanged.
10. Follow the conventions of this repository, in the code and in the prose.

### Existing translations

A change that improves an existing translation is welcome. The same rules apply.

## Message rules

- Write a complete sentence. One message, one point.
- Give translators the whole sentence with one placeholder per value. Never join two messages to build one sentence.
- Keep the placeholders of a translation in the same count as the default catalogue. `T.F` formats with the values the caller passes.
- Follow [the simple-english skill](../skills/simple-english/SKILL.md), with British English spelling for the catalogues written in British English.
- Keep identifiers, flag names, format names, and quoted errors unchanged, in every locale.
- Do not write em-dashes or en-dashes in any message.

Messages cover the command line only. The library returns errors and loss reports, which are not translated. [The usage page](usage.md) shows where each message appears.

## Tests

[The i18n tests](../internal/i18n/i18n_test.go) cover the tag resolution, the register and lookup path, the key fallback, the locale report, and the completeness of the second catalogue. The message catalogue sits at 100 percent statement coverage with the rest of the module.
